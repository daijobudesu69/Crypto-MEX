## Kenapa audit ini ada

Dalam 3,5 hari pertama beroperasi, **32 dari 32 run sinyal berstatus
`no_events`** — belum ada satu pun SIGNAL yang benar-benar terkirim. Artinya
seluruh jalur pengiriman sinyal, penanganan konflik `events.csv`, dan pemulihan
rebase **belum pernah dieksekusi di produksi**. Semua temuan kritis di bawah
berada tepat di jalur yang belum teruji itu, dan akan aktif pertama kali justru
saat sinyal asli pertama muncul.

Sementara itu `state/runs.csv` sendiri menunjukkan cron hanya berjalan 23–26%
dari jadwal.

## Bukti — kenapa cron harus diganti

Diukur ulang pada 4 Sep 2026, setelah gelombang perbaikan pertama:

```
Jendela 3 Sep 00:00 – 4 Sep 02:00 UTC (26 jam)
run terjadwal benar-benar jalan : 12
seharusnya jalan                : 46
KEANDALAN CRON                  : 26%     (jeda terburuk 4:47:52)

Cakupan tiap bar 4H (jendela kirim = bar tutup -> sinyal hangus):
  bar 02 Sep 20:00   tutup 00:00  hangus 04:00   1 run   ok
  bar 03 Sep 00:00   tutup 04:00  hangus 08:00   2 run   ok
  bar 03 Sep 04:00   tutup 08:00  hangus 12:00   2 run   ok
  bar 03 Sep 08:00   tutup 12:00  hangus 16:00   0 run   <<< SINYAL DI BAR INI HILANG
  bar 03 Sep 12:00   tutup 16:00  hangus 20:00   3 run   ok
  bar 03 Sep 16:00   tutup 20:00  hangus 00:00   3 run   ok
  bar 03 Sep 20:00   tutup 00:00  hangus 04:00   1 run   ok
```

Bar 4H baru tutup 4 jam setelah dibuka, dan sinyalnya hangus 8 jam setelah bar —
jadi jendela kirim efektif cuma **4 jam**, lebih pendek dari jeda terburuk.
Sinyal LONG nyata pertama selamat hanya karena kebetulan muncul satu bar setelah
lubang itu.

## Kritis — sinyal bisa hilang atau dobel

| # | Problem | Blocker | Solution | Status |
|---|---|---|---|---|
| **C1** | **Telegram gagal = sinyal hilang permanen, job tetap hijau.** `notify.send()` mengembalikan `False` dan tidak pernah melempar; `main()` tetap memajukan `last_bar` lalu `return 0`. | Tidak ada retry, outbox, atau exit code non-nol. Bar sudah ditandai selesai sehingga run berikutnya melewatinya. Satu timeout 25 detik = satu sinyal hilang selamanya, jejaknya cuma `telegram_ok=False` di CSV yang tidak ada yang membaca. | Outbox di `state.outbox`: pesan ditulis dulu, dihapus hanya setelah Telegram menerima, kuncinya masuk `state.sent_ids`. Retry tiap run sampai berhasil atau hangus. | ✅ |
| **C2** | **Pesan dikirim sebelum state disimpan → risiko pesan dobel.** Urutannya kirim → tulis state → commit/push, kegagalan di antaranya membuat bar diproses ulang. | README menjanjikan "tidak ada pesan dobel", tapi jaminan itu hanya berlaku kalau push berhasil. `timeout-minutes`, runner mati, atau push gagal 5× membatalkan penyimpanan state *setelah* pesan sampai. | Dedup berbasis `signal_id`: `sent_ids` diperiksa sebelum kirim, jadi pemutaran ulang aman berapa kali pun. Jauh lebih murah daripada mengejar atomicity antara Telegram dan git. | ✅ |
| **C3** | **`git rebase --skip` membuang state run ini diam-diam.** Kalau `--continue` gagal, fallback `--skip` menghapus commit run ini; loop lalu push (sukses) dan mencetak "state tersimpan". | Kegagalan **melapor sukses**. Baris ledger hilang padahal Telegram sudah terkirim, dan `last_bar` mundur → bar sama diproses lagi → pesan dobel. Ledger dan Telegram tidak sinkron tanpa peringatan. | `--skip` dihapus. Kalau `--continue` gagal: `rebase --abort`, ulangi siklus penuh, dan kalau tetap gagal setelah 5× biarkan job merah. Jangan pernah exit 0 setelah membuang data. | ✅ |
| **C4** | **Pesan alert error justru ditolak Telegram.** `alert_message()` menyisipkan teks exception mentah ke `<code>` dengan `parse_mode="HTML"`. | Terkonfirmasi: exception berisi `<b>` / `&` → `400 can't parse entities` → alert gagal **justru saat data feed mati**, momen ketika alert itu satu-satunya yang tersisa. Bug sama ada di baris `warn` heartbeat. | `notify.esc()` (`html.escape`) untuk semua teks dinamis di `alert_message()` dan `heartbeat_message()`. | ✅ |
| **C5** | **Run yang gagal menghapus jejaknya sendiri.** Langkah "Simpan state" tidak punya `if: always()`; saat `run_signal.py` exit 1 langkah commit dilewati. | Baris `runs.csv` yang sudah ditulis tepat sebelum `return 1` tidak pernah ter-commit. **Justru run bermasalah yang absen** dari catatan liveness, memberi gambaran kesehatan yang terlalu optimistis. | `if: always()` pada langkah simpan state di kedua workflow. Exit code 1 dipertahankan agar job tetap merah. | ✅ |

## Tinggi — state rapuh & penjadwalan tidak memadai

| # | Problem | Blocker | Solution | Status |
|---|---|---|---|---|
| **H1** | **Cron cuma jalan 23–26%, jeda terburuk melewati jendela kirim.** Lubang 4j48m pada 3 Sep menelan habis jendela kirim bar 08:00. | Bukan risiko teoretis — sudah terjadi. Dengan hanya ~3,7 sinyal/bulan, kehilangan satu merusak ukuran sampel forward test. Outbox tidak menolong: masalahnya run-nya memang tidak pernah jalan. | **Pola dibalik.** Cron tidak lagi mengecek — tugasnya hanya *menyalakan* pemantau yang hidup ~5j30m dan mengecek sendiri tiap 10 menit. Satu cron yang berhasil menutupi 5,5 jam; jadwal yang jatuh saat pemantau hidup akan antre lalu langsung mulai setelahnya. Repo publik ⇒ menit Actions tak dibatasi. | ✅ |
| **H2** | **`write_json` tidak atomik → state bisa korup permanen.** `open(path,"w")` memotong file dulu, baru menulis. | `read_json` melempar `JSONDecodeError` dan pemanggilnya tidak punya try/except: seluruh run crash sebelum sempat menulis `runs.csv` atau mengirim alert. `timeout-minutes: 10` adalah pembunuh persis seperti ini. | Tulis ke `path.tmp` + `os.fsync` + `os.replace` (atomik di semua OS). `read_json` melempar `StateCorrupt`, **tidak** mengembalikan default — default akan tampak seperti run pertama dan meninggalkan posisi terbuka tanpa stop. | ✅ |
| **H3** | **Header CSV bisa melenceng dan merusak file selamanya.** `_append()` hanya menulis header kalau file belum ada. | `DictWriter` menulis posisional, jadi baris 43-kolom di bawah header lama membuat `pd.read_csv` melempar `ParserError`. Lebih buruk: `_counts()` di heartbeat memanggil `read_csv` tanpa try/except, jadi satu perubahan skema mematikan heartbeat harian juga. | Header divalidasi tiap append; kalau berbeda, log lama dirotasi ke `events.v1.csv` dan file baru dimulai bersih. `_counts()` dibungkus try/except. | ✅ |
| **H4** | **`checkout --theirs` justru memilih state yang lebih lama.** Komentarnya mengklaim run ini "sudah memproses bar paling akhir". | Di jalur retry justru sebaliknya: push kita ditolak *karena* run lain push duluan — merekalah yang lebih baru. Memaksa milik kita bisa memundurkan `last_bar` → bar diproses ulang → pesan dobel. | `tools/merge_state.py`: `last_bar` terbaru menang (beserta `position`/`pending` dari sisi yang sama), `sent_ids` di-union, `outbox` di-union minus yang sudah terkirim. Hasilnya tidak bergantung sisi rebase. | ✅ |
| **H5** | **Checkout dangkal membuat retry rapuh.** `actions/checkout@v4` default `fetch-depth: 1`. | Rebase di atas clone dangkal bisa gagal menemukan merge base. **Jalur pemulihan konflik paling mungkin gagal tepat saat dibutuhkan**, lalu jatuh ke `--skip` yang membuang data (C3). | `fetch-depth: 0` di kedua workflow yang melakukan push. | ✅ |

## Yang masih jadi batas

Kalau pemantau mati (runner dibunuh, habis waktu, gagal start), cakupan
bergantung lagi pada cron `7,37 * * * *` yang tunduk pada keandalan GitHub ~25%.
Bedanya sekarang: lubang itu harus terjadi **tepat saat tidak ada pemantau yang
hidup**, bukan tiap kali cron meleset. Heartbeat harian memperlihatkannya lewat
`bar terakhir diproses` yang tertinggal.

Lapis berikutnya kalau masih kurang: pemicu eksternal (cron-job.org atau
Cloudflare Worker) yang memanggil `workflow_dispatch` lewat API GitHub memakai
Personal Access Token ber-scope `actions:write`.
